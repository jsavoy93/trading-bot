## Step 1 — Fix 1: event-log flood (unresolved audit rows on every loop)

### Problem
`poll_order_fills()` appends an `order_events` row (`unresolved = 1`) for every
unresolved order on EVERY analysis loop (~10-17 s). One stuck order therefore
produced thousands of identical rows per day — an unusable audit trail and
unbounded table growth.

### Fix
1. **Deterministic outcome class** (`src/core/smart_bot.py`):
   - `OUTCOME_BROKER_UNREACHABLE = "broker-unreachable"` — the fetch raised, or the
     broker returned nothing usable (also covers a client without a single-order
     fetch API);
   - `OUTCOME_UNRECOGNIZED_STATUS_PREFIX = "unrecognized-status:"` → the class is
     `unrecognized-status:<raw_status>` — the broker answered with a raw token the
     bot does not recognize (the token is embedded so outcomes stay
     distinguishable);
   - `OUTCOME_RECONCILE_EXCEPTION = "reconcile-exception"` — reconciliation itself
     failed.
   - `_unresolved_outcome_class(broker_event, fetch_failed)` maps the poll facts to
     exactly one class. The class is DETERMINISTIC: no error text, no timestamp
     (the error text goes to the log; the class goes to the audit row).
2. **Change detection** (`_record_unresolved_event`): a row is written ONLY when the
   class differs from that order's MOST RECENT `order_events` row. The comparison
   is a DB query, not in-memory state, so it survives a process restart.
3. **Storage**: the class is stored verbatim in the EXISTING
   `order_events.event_note` column — no new table, no new column. `raw_status`
   still carries the broker's raw token when the broker answered, so nothing is
   lost on the unrecognized-status path.
4. **New DB method** (`src/database/sqlite_db.py`): `get_last_order_event(trade_id)`
   → `SELECT * FROM order_events WHERE trade_id = ? ORDER BY id DESC LIMIT 1`
   (indexed by `idx_order_events_trade_id`).
5. **Unchanged**: resolved transitions are still written by `update_trade_lifecycle()`
   exactly as before (`unresolved = 0`); the trades row is still never modified by an
   unresolved poll; the poller still never submits, cancels or replaces anything.
6. **Heartbeat: NOT implemented** (the owner marked it optional; the owner's stated
   fallback — "a test that no extra rows are written" — is implemented instead).
   Consequence, documented in MENTOR.md: an order stuck unresolved keeps exactly ONE
   audit row and produces no further audit evidence; the poller keeps polling it and
   the trades row still carries the real lifecycle state.

### Follow-on consequence to know
Changing the class strings later makes every unresolved order write one additional
row on its next poll (the new class differs from the stored one). Noted in MENTOR.md.

## Step 2 — Fix 2: NULL-timestamp loose end

`get_pending_fill_trades()` re-polls CANCELED / EXPIRED rows younger than 24 h. The
predicate used `julianday(COALESCE(order_updated_at, created_at)) IS NULL` as a
pass-through, so a row whose `order_updated_at` AND `created_at` are both NULL (no
usable age) was re-polled forever. The pass-through is removed: such a row is now
treated as OLD and is NOT re-polled. Non-terminal rows are unaffected by the horizon
(they are selected by status, not by age).
