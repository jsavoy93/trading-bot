Source of truth: `src/core/smart_bot.py` lines ~3134-3160

| 3 | MACD_histogram > 0 | strict greater-than 0 (the histogram, not the line) | structural |
| 4 | volume_ratio >= 1.0 | relative to 20-day average volume | **only when `enable_volume_confirmation=True`** |

All four must be TRUE simultaneously for the inline `buy_eligible`
expression to evaluate True. Any single failure → `buy_eligible = False`.

### B. CONFIG-CONDITIONAL CONDITIONS

- **`volume_confirmation`** (gate #4 above) is the only config-conditional
  daily BUY condition. The relevant setting is
  `enable_volume_confirmation` in `src/core/settings_service.py`
  (line 95-96, default `True`). The runtime helper
  `_buy_funnel_required_gates_runtime()` in `dashboard.py` reads this
  setting per-request. With production default = True, the volume gate
  IS required. If an owner flips the setting to False, the volume
  gate is removed from the required set in real time.
- **CURRENT setting:** `enable_volume_confirmation = True`
  (production deployment default; verified in
  `src/core/settings_service.py` and `src/core/smart_bot.py` line 471).

### C. MTF FINAL-SIGNAL CONDITIONS (downgrade + agreement gates)

In multi_timeframe mode (the production default), `daily_signal` and
`hourly_signal` must **agree** on the final signal:

```
if daily_signal == hourly_signal:
    if daily_signal == "BUY":
        # proceed to ranking + execution
```

- If `hourly` is absent/unavailable: code falls back to `daily_only`
  mode (no SELL race against hourly); BUY is still emit-able from
  daily alone.
- If `daily_signal != hourly_signal` (daily BUY, hourly SELL/HOLD or
  vice versa): the cycle emits HOLD with the persisted
  `decision.outcome = "HOLD_INELIGIBLE"` (multi_timeframe path).
- The `decision.outcome` value, `timeframe_mode`, `signal_strength`
  ARE persisted. `daily_signal` / `hourly_signal` / explicit MTF
  agreement state ARE NOT persisted — these are code-path inferences
  only.

### D. SCORING / RANKING CONDITIONS (after BUY emission, not gating)

- `scoring.total_score` (0..100) is **NOT** a gate to emit BUY.
  SCORE-002 removed the previous score-derived sub-gate. It is the
  published quality rank and may NOT independently turn an otherwise
  eligible BUY into HOLD.
- `total_score` IS used for signal **strength** ONLY:
  - score >= 65 → STRONG
  - score <  65 → MEDIUM
- `rsi_score`, `sma_score`, `macd_score`, `bb_score`,
  `catalyst_score`, `regime_score`, `insider_boost`,
  `volatility_tier/multiplier` are SCORING components. They are NOT
  BUY-eligibility gates. They appear in the dashboard scoring block
  for observability only.
- Ranking conditions (`ranking.applicable`, `candidate_rank`, etc.)
  are applied AFTER signal emission and only affect which BUYs get
  promoted to the execution queue.

### E. EXECUTION-ONLY CONDITIONS (post-emission, post-ranking)

- Earnings filter (skip BUY within `earnings_days_skip` of earnings).
- SP relative strength filter (stock must outperform SPY).
- Trading-window filter (time-of-day allowed).
- Liquidity, cooldown, position sizing, order submission — all
  execution-stage, do not affect whether `signal == "BUY"` is emitted.

### SCORE-002 explicit confirmation

YES, `scoring.total_score` participates in BUY emission, BUT only
in determining STRONG vs MEDIUM **strength**, NOT in determining
whether `signal == "BUY"`. The eligibility expression does NOT read
`total_score`.

### MACD explicit confirmation

YES, MACD participates in BUY emission. The condition is
`MACD_histogram > 0` (strict greater-than-zero). It is NOT optional
in current code. If the histogram is zero or negative, BUY is not
emitted. If MACD data is unavailable, the analyzer returns HOLD
(buy_eligible short-circuits to False because the gate check is
`macd_hist_for_gate is not None and pd.notna(macd_hist_for_gate)
and float(macd_hist_for_gate) > 0`).

### Volume explicit confirmation

YES, volume participates in BUY emission when
`enable_volume_confirmation=True` (production default).
The condition is `volume_ratio >= 1.0` (today's volume / 20-day
average). If volume data is unavailable, `buy_eligible` short-circuits
to False (same pattern as MACD). When the setting is False, the
volume gate is OMITTED from `buy_eligible` and absent volume data
does not block BUY.

## 5. NEAR-MISS FINAL SEMANTICS — confirmed

The implementation in `api_buy_funnel_near_miss` now means:

```
For each SYMBOL with a decision_history row in the selected range:
    1. Find the LATEST decision_history row per symbol via
       NOT EXISTS correlated subquery against the same cohort window.
       (latest = no later (cycle_start, id) in the cohort)
    2. Evaluate the near-miss contract against THAT row only:
       - outcome is NOT SKIPPED_INVALID_DATA
       - signal is NOT SELL
       - ALL currently-required BUY gates have an applied=1 row recorded
         (applied_required_n = required_count)
       - Exactly ONE required gate has applied=1 AND passed=0 (failed_n = 1)
       - Every OTHER required gate has applied=1 AND passed=1
         (failed_n + passed_required_n = applied_required_n, no orphans)
    3. Symbol appears AT MOST ONCE in the response.
    4. Older qualifying near-miss state CANNOT be surfaced when a
       newer non-near-miss state for that symbol exists in the window
       (proven by test_near_miss_dedup_latest_state_blocks_older).
```

Scoring (total_score) is shown as context only — NOT an eligibility
gate (SCORE-002). Execution blockers do not produce BUY near-misses
(this endpoint is BUY-only by definition).

## 6. CURRENT REQUIREMENTS vs HISTORICAL APPLIED TRUTH

The owner asked: why were `macd_positive` and `volume_confirmation`
absent / `applied=0` in previously-inspected joint-pass rows if
current BUY code requires them?

The persistence and code-emission are SEPARATE:
- **Code-emission requires both** (gates #3 and #4 in section 2.A).
- **Persistence only happens when the analyzer evaluates them**:
  - `macd_positive` row is written in `_build_decision_snapshot` ONLY
    when `macd_hist_for_gate is not None and pd.notna(macd_hist_for_gate)`.
    If the analyzer reached BUY-eligibility evaluation AND the data
    was present, the row was persisted with `applied=1`. If the
    analyzer short-circuited earlier (e.g. RSI/SMA NaN) without
    fetching MACD, no row was written — `applied=0` / absent.
  - `volume_confirmation` row is written ONLY when
    `enable_volume_confirmation AND volume_ratio is not None AND
    pd.notna(volume_ratio)`. If volume data was missing at analysis
    time, no row was written.

Therefore "absent / applied=0" in a persisted row can mean:
1. **Condition required but analysis terminated before evaluation.**
   This is the most common case for macd_positive in fallback HOLD
   rows (analyzer short-circuited on missing RSI/SMA data).
2. **Condition config-disabled at evaluation time.**
   For volume_confirmation: if `enable_volume_confirmation` was False
   in some past cycle, no volume row was persisted.
3. **Condition evaluated but data unavailable** at the moment the
   analyzer ran the gate check (data quality / partial bar).
4. **Fallback artifact.** When `analyze_symbol` returns None (no
   data), the `_persist_skipped_terminal_decision` writes a HOLD
   fallback with `outcome=SKIPPED_INVALID_DATA`. The fallback path
   may or may not write RSI/SMA rows (depending on where the short
   circuit happened); MACD/volume are typically NOT evaluated.
5. **Observability gap.** The `_build_decision_snapshot` may have
   been called BEFORE MACD/volume were attempted.

The previous examples (MUYY MUST MUNY NAUT NACP MYY MYXXW MYXXU)
were captured during the v0.1 run and represent cases 1 / 4 / 5 —
where the persisted RSI/SMA rows are present and passed, but the
absent MACD/volume rows were not evaluated or were post-analyzer
short-circuited. Under the v0.2 contract, these symbols' rows do
NOT qualify as valid near misses because `applied_required_n =
required_count` excludes rows where macd or volume is absent.

This distinction is exactly why the v0.2 contract is the correct
one: those v0.1 examples conflated "fallback HOLD artifacts with
RSI+SMA persisted" with "real BUY-eligibility near misses" — they
are NOT the same thing.

## 11. FINAL OWNER QUESTIONS

**Q: Is BUY reachable in current code?**

**Q: What EXACT conditions currently have to be satisfied for SmartBot to emit BUY?**
1. RSI < `rsi_buy_threshold` (default 30; `settings_service.py`)
2. SMA_fast > SMA_slow (structural, no scalar config)
3. MACD_histogram > 0 (structural, no scalar config)
4. volume_ratio >= 1.0 (only when `enable_volume_confirmation=True`; default True)

AND (multi_timeframe mode only):
5. hourly_signal == daily_signal == "BUY"

All four daily conditions must be evaluated AND passed (no absent
required gates). If MACD or volume data is missing at analysis time,
`buy_eligible` short-circuits to False.

**Q: Are RSI + SMA sufficient to emit BUY?**
NO. Both MACD and volume_confirmation are also required under the
current code with production-default config. The previous
`{rsi_oversold, sma_uptrend}` set was incomplete — this was the
owner-flagged contradiction, now resolved.

**Q: What roles do MACD and volume play?**
Both are HARD daily BUY gates (non-bypassable, no score-derived
modifier). MACD is always required; volume is required when the
config flag is True. They are not advisory, not scoring components,
not optional.

**Q: What role does MTF play?**
MTF is a final-signal agreement gate. After the daily BUY check
succeeds, in multi_timeframe mode the hourly signal must agree;
otherwise HOLD is emitted. In daily_only mode (hourly unavailable),
BUY can be emitted from daily alone.

**Q: Does total_score gate BUY eligibility?**
NO. SCORE-002 forbids it. `total_score` is used ONLY to discriminate
STRONG (>=65) vs MEDIUM (<65) signal strength AFTER `signal == "BUY"`
has been emitted. It cannot independently turn an eligible BUY into
HOLD, nor turn HOLD into BUY.

**Q: Why did the previously observed RSI+SMA-pass population still produce zero BUYs?**
The RSI+SMA joint-pass population (~1,300 in 24h) feeds into the
analyzer's BUY check, which fails because (a) MACD/volume are
absent in many of those rows (fallback artifacts and short-circuits),
and (b) of the valid ~528, the multi-timeframe / no-action path
downgrades them to `HOLD_INELIGIBLE`/`WEAK`. The choke point is at
the buy_eligible check (MACD/volume presence) AND at the MTF
agreement step, NOT at execution.

**Q: How much of that explanation is directly persisted versus inferred from code?**
- DIRECTLY PERSISTED: `signal`, `outcome`, `timeframe_mode`,
  `signal_strength`, `primary_reason`.
- INFERRED FROM CODE: that the downgrade happened at the buy_eligible
  expression (because macd/volume are absent or fail) AND/OR at the
  MTF agreement step (because hourly_signal disagrees with daily).
- UNKNOWN: which of (macd_absent vs macd_negative) actually occurred
  for each row, and the exact hourly-side value.

**Q: Is the final near-miss definition now truthful?**
YES. The v0.2 contract:
- Latest state per symbol (NOT older state shadowed by newer
  non-qualifying state).
- All currently-required BUY gates applied + passed, except exactly
  one which is applied + failed.
- No SELL signals, no SKIPPED_INVALID_DATA outcomes.
- Score is context-only.
This matches the BUY-eligibility contract minus exactly one required
