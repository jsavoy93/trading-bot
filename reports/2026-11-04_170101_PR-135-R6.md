## 2. Root-cause analysis

### 2.1 Reused protective-sell label

`runner._reprotect_shares` (round-5 code, pre-fix):

```python
gen = int(t.get("stopgap_gen", 1)) + 1
if gen == 2 and t.get("stopgap_client_order_id"):
    gap_coid = make_stopgap_replace_client_order_id(RSI2, sym, t["date"], t["n"], gen)
else:
    gap_coid = make_stopgap_client_order_id(RSI2, sym, t["date"], t["n"])
...
if gap_resp.get("error") or not gap_resp.get("id"):
    ... return False          # <-- t["stopgap_gen"] NOT updated
t["stopgap_client_order_id"] = gap_coid
t["stopgap_gen"] = gen        # <-- only on success
```

Two independent defects:

- **D1 — label reuse for gen >= 3.** The `else` branch produced the plain
  `-stopgap` label for gen 3, 4, 5, ... That is a `client_order_id` Alpaca has
  already seen -> the broker rejects the sell -> the position stays unprotected
  and the runner keeps retrying the same dead label forever.
- **D2 — the generation counter was not persisted on a failed submit.** The
  counter was written only on success. A failed submit still may have consumed
  the label at the broker, so the next run recomputed the SAME generation and
  re-sent the same label.

A third, related defect was found while implementing the fix (**D3**):

- **D3 — `place_stops_after_fill` reset the counter to 1.** That path set
  `t["stopgap_gen"] = 1` unconditionally. After a failed re-protection the
  trade has no stop order id, so `place_stops_after_fill` DOES run again on the
  next run and reset the counter to 1 -> the plain `-stopgap` label was re-sent
  after `-stopgap-r2` had already been used. Both code paths therefore have to
  share ONE counter.

### 2.2 Execute gate anchored on the UTC date

`runner._c4_evidence_window_start` (pre-fix):

```python
return datetime(now.year, now.month, now.day, C4_EVIDENCE_UTC[0], C4_EVIDENCE_UTC[1], tzinfo=timezone.utc)
```

The C4 timer (`strat023-c4-shadow.service`) fires at **21:15 UTC**, which is
**16:15 ET on the SAME US/Eastern calendar day**. The evidence window must
therefore start at 21:00 UTC of the *trading* day.

A run at 6 PM CST is `00:00 UTC` on the **next UTC day** but still **7 PM ET
on the same trading day**. The old code built the window from the UTC calendar
date, so the window became `21:00 UTC of the NEXT day` — the journal entry of
the C4 run that actually traded the session (21:15 UTC of the trading day) was
filtered out, the gate saw no evidence, and the evening run was REFUSED even
though C4 had already finished for the session.

Verified with the host tz database:

| UTC clock | US/Eastern | same ET trading date? |
|---|---|---|
| 2026-11-03 21:30Z | 2026-11-03 16:30 ET | yes |
| 2026-11-03 23:30Z | 2026-11-03 18:30 ET | yes |
| 2026-11-04 00:00Z | 2026-11-03 19:00 ET | **yes** (the 6 PM CST case) |
| 2026-11-04 01:30Z | 2026-11-03 20:30 ET | yes |
| 2026-11-04 21:30Z | 2026-11-04 16:30 ET | no — new trading day |

## 3. Implementation

### 3.1 `experiments/swing_paper/runner.py`

**New helper — US/Eastern trading date**

```python
US_EASTERN = ZoneInfo("America/New_York")

def us_eastern_trading_date(now: datetime):
    if now.tzinfo is None:
        now = now.replace(tzinfo=timezone.utc)
    return now.astimezone(US_EASTERN).date()
```

**ET-anchored evidence window**

```python
def _c4_evidence_window_start(now: datetime) -> datetime:
    d = us_eastern_trading_date(now)
    return datetime(d.year, d.month, d.day, C4_EVIDENCE_UTC[0],
                    C4_EVIDENCE_UTC[1], tzinfo=timezone.utc)
```

**`_reprotect_shares` — generation always carried, always persisted**

```python
gen = max(int(t.get("stopgap_gen", 0)) + 1, 2)
t["stopgap_gen"] = gen
gap_coid = make_stopgap_replace_client_order_id(RSI2, sym, t["date"], t["n"], gen)
gap_resp = api.submit_order({...})
if gap_resp.get("error") or not gap_resp.get("id"):
    t["stopgap_client_order_id"] = gap_coid   # the label was USED
    ... return False
t["stopgap_client_order_id"] = gap_coid
t["stopgap_pending"] = {...}
```

Notes:
- `max(..., 2)` guarantees a re-protection NEVER uses the plain `-stopgap`
  label — the plain label belongs to the first gap sell only.
- The counter is written BEFORE the submit, so a failed submit still advances
  it.
- `t["stopgap_client_order_id"]` is recorded on failure too, so the label is
  never re-sent.

**`place_stops_after_fill` — bump, never reset**

```python
gen = int(t.get("stopgap_gen", 0)) + 1
t["stopgap_gen"] = gen
if gen <= 1:
    gap_coid = make_stopgap_client_order_id(RSI2, sym, t["date"], t["n"])
else:
    gap_coid = make_stopgap_replace_client_order_id(RSI2, sym, t["date"], t["n"], gen)
...
if gap_resp.get("error") or not gap_resp.get("id"):
    ...
    t["stopgap_failed"] = True
    t["stopgap_client_order_id"] = gap_coid
```

The counter is now shared with `_reprotect_shares` and is never reset
downwards (fixes D3).

## 7. Risks

1. **Pre-existing environmental test failure** (documented above) — not caused
   by this change, present on the base commit.
2. **Label-shape change.** A re-protection sell now carries `-stopgap-r<gen>`
   instead of the plain `-stopgap`. `parse_label` already handled
   `-stopgap-r<k>` for every k (verified: `rsi2-AMD-20261103-1-stopgap-r2`,
   `-r3`, `-r12` all parse to `kind='stopgap'`), so `report_pnl` attribution
   is unaffected. Label length stays well inside the 48-char Alpaca limit
   (27 chars for the plain label, 30-33 for `-stopgap-r<gen>`).
3. **The execute gate window widens** for evening runs on the same trading
   day. It does NOT widen before C4 has actually finished for the session —
   `test_execute_gate_still_refuses_before_c4_finished_for_the_session`
   pins that.
4. **`zoneinfo` dependency** on the host tz database for
   `America/New_York`. Present on this host (the tz database resolves in the
   tests) and part of the Python 3.9+ standard library.
5. **Historical orders** sent under a reused label were rejected by Alpaca at
   the time and never filled, so there is no position impact and nothing to
   reconcile.
6. **No live-trading validation.** The changes are verified by unit tests with
   a fake broker only; the first real paper run after merge is the operational
   proof.
