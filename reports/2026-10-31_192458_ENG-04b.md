## 5. Per-failure disposition

Every one of the 40 baseline failures, with its real root cause and the

### 5.1 Wall-clock-dependent synthetic data (30 failures)

**Root cause.** The dashboard's read endpoints filter rows with a range
window whose cutoffs are computed from `datetime.now(timezone.utc)`
(`_phase_c_range_clause` / `_p0` range handling): `today`, `24h`, `7d`. The
synthetic fixtures inserted `cycle_start` values pinned to fixed calendar
dates in September 2026. Once real time advanced past those dates, every
synthetic row fell outside every window and the endpoints returned zero rows.
The tests then failed with "expected 6, got 0"-style assertions — failures
caused by the clock, not by the behaviour under test.

**Evidence.** Baseline traceback for
`test_near_miss_rsi_pass_sma_fail_IS_near_miss`:

    E       AssertionError: expected 6 near misses, got 0
    E       assert 6 == 0

with the dashboard returning an empty list rather than the fixture rows.

**Fix.** Anchor the synthetic datasets to `now()` instead of a fixed date,
preserving relative ordering where the test depends on it. The repository
already contained the correct pattern — `tests/test_dashboard_phase_c_obs_analytics.py`
had a `_now_iso()` helper and a `phase_c_dataset_windowed()` dataset
explicitly built for this reason. The same pattern was applied consistently.

Details per file:

- `tests/test_dashboard_p0_buy_blockers.py` — added `_now_iso(offset_seconds)`.
  Replaced 10 hardcoded `2026-09-30T15:xx:00+00:00` literals with
  `_now_iso()`. The pagination test's "unique, DECREASING `cycle_start`"
  requirement is preserved via `_now_iso(offset_seconds=-i * 60)`.
  The 24h-vs-48h test keeps its "old rows excluded" semantics because its
  old rows are anchored to `now() - 48h` (the file already computed this
  relative to `now()`).
- `tests/test_dashboard_phase_c_obs_analytics.py` — converted the module-level
  `_PHASE_C7_DEFAULT_DECISION_ROWS` / `_PHASE_C7_DEFAULT_FUNNEL_ROW`
  constants into `_phase_c7_default_decision_rows()` /
  `_phase_c7_default_funnel_row()` factories (timestamps now computed at call
  time, not import time). Added `_now_iso()` and `_phase_c7_at(index,
  offset_seconds)` helpers. Replaced 6 inline `2026-09-15T…` literals and 44
  `2026-09-24T10:00:0X+00:00` literals (3 distinct values, 26/14/4
  occurrences) preserving their relative ordering.
- `tests/test_buy_funnel_dashboard.py` — added `_sql_ts(offset_seconds)`
  returning a pre-quoted SQL literal, plus `_TS_MAIN` / `_TS_OLDER` /
  `_TS_NEWER`. Replaced 66 literals (50× `19:00:00`, 10× `18:00:00`,
  6× `20:00:00`). 28 single-line `cur.execute("…")` calls were converted to
  f-strings; 11 embedded `'{}'` literals were escaped as `'{{}}'`; 3 rows
  whose payload embeds JSON with escaped double quotes were rewritten to use
  SQL parameter binding instead (an f-string cannot contain `\"` safely).

**Special case — `phase_c_dataset_coverage()`.** This dataset must produce one
cycle strictly BEFORE the OBS-002 deployment boundary
(`2026-09-14T20:24:55`) and one after. Because the boundary is a fixed
historical constant, no timestamp can simultaneously be before it AND inside
a `now()-7d` window. The pre-OBS-002 cycle therefore keeps a fixed
pre-boundary timestamp (that is the semantic point of the dataset), while the
post cycle is `now()`-anchored. The window-sensitive assertions already have
their own dedicated dataset (`phase_c_dataset_coverage_windowed()`), whose
docstring explains this exact constraint.

**Status:** FIXED (30/30).

### 5.2 `POST /api/settings` route accidentally deleted (3 failures)

**Root cause.** `git log -S api_update_settings -- dashboard.py` showed the
route was introduced in `8b87589` and removed in `25a82c5` (PR #101, "BUY-FUNNEL
DASHBOARD v0"). The PR #101 diff shows the `@app.post("/api/settings")` /
`def api_update_settings` block was *replaced* by a 1424-line insertion of the
BUY-FUNNEL endpoints — i.e. collateral damage in a large edit, not an
intentional removal. Its helpers `_validate_dashboard_settings_batch` and
`_persist_dashboard_settings_batch` were left in `dashboard.py` unused, and
`_refresh_trading_params` was still called by the surviving `GET /api/settings`.

**Corroboration that it was a real live bug, not a removed feature:**
`templates/dashboard.html` still contains three `fetch('/api/settings', {method:
'POST', …})` calls (`updateSetting`, `toggleBoolSetting`, `resetSetting`) and
each expects `result.status === 'ok'`. With the route absent, every settings
write in the dashboard returned **HTTP 405 Method Not Allowed** — the Settings
UI could not save anything.

**Fix.** Restored the route verbatim from the pre-#101 revision
(`git show 25a82c5^:dashboard.py`), with an ENG-04b comment documenting the
origin.

**Verification.** Functional check against the worktree build:

    POST /api/settings {"sma_fast":"12.0","enable_volume_confirmation":"off"}
      -> 200 {'updated': {'sma_fast': 12, 'enable_volume_confirmation': False}, 'status': 'ok'}
    POST /api/settings {"hourly_weight": 2}
      -> 400 {'detail': 'hourly_weight must be <= 1.0'}
    persisted sma_fast: 12

Registered routes: `('/api/settings', ['GET'])` and `('/api/settings', ['POST'])`.

**Status:** FIXED (3/3). Also repairs a live production defect.

### 5.3 Status legend contradicted the status dot (1 failure)

**Root cause.** In `templates/dashboard.html` the navbar *dot* priority was
`fully_ready` → `alpaca_api_reachable` → red, but the *legend* priority was
`fully_ready` → `smartbot_runner_active` → `alpaca_api_reachable` → "API
Offline". With the runner service active and Alpaca unreachable, the dot was
red (tooltip "Alpaca paper API is unreachable") while the legend read
"Runner Active, No Session".

This was a latent defect from the commit that introduced both the test and
the template (`4d7de83`, BOT-001 #75) — it only surfaces when
`smartbot_runner_active=True` AND `alpaca_api_reachable=False`, i.e. on a host
where the runner is up but the API is down.

**Fix.** Legend priority now mirrors the dot: `fully_ready` → "Running";
`not alpaca_api_reachable` → "API Offline"; `smartbot_runner_active` →
"Runner Active, No Session"; else → "API Online, Bot Off".

**Status:** FIXED (1/1). Also repairs a live UI-truthfulness defect.

### 5.4 Weekend / after-hours trading-window gate (3 failures)

**Root cause.** `src/core/smart_bot.py` (line ~4149) gates a BUY on:

    from src.analysis.trading_windows import is_trading_allowed
    allowed, time_reason = is_trading_allowed()
    if not allowed: signal = "HOLD"

`is_trading_allowed()` returns `(False, "Weekend - market closed")` when
`weekday() >= 5`. The task ran on **Saturday 2026-10-31**, so three
SCORE-002 tests asserting `result["signal"] == "BUY"` failed:

    ⏰ TEST: Blocked by trading window (Weekend - market closed)
    E   AssertionError: expected BUY (SCORE-002 separates eligibility from
        score), got signal=HOLD, total_score=79.12748420070893

The score was 79 — eligibility was reached and correct; the window check
downgraded the signal afterwards.

**Fix.** Added an **autouse** fixture to
`tests/test_score_002_eligibility_and_ranking.py` that monkeypatches
`src.analysis.trading_windows.is_trading_allowed` to `(True, "Trading
allowed")`. The patch is effective because `smart_bot` performs the import
*inside* the function, resolving the attribute on the package module at call
time. Autouse is appropriate because no test in that module concerns the
trading-window calendar — leaving it to the real clock made the entire
module fail on weekends and outside 09:45–15:45 ET.

**Status:** FIXED (3/3).

**Status:** FIXED (2/2). This was a test-isolation defect that also masked

### 5.6 Hardcoded `cwd` + non-existent `LOCK_FILE_OVERRIDE` (1 failure)

**Root cause.** Two independent defects in
`tests/test_bot002_paper_only_guard.py::test_main_py_installs_sigterm_handler`:

1. The subprocess ran with `cwd="/root/.openclaw/workspace/trading-bot"`, so
   `import main` resolved to the workspace copy, not the code under test.
2. The test set `LOCK_FILE_OVERRIDE`, but `main.py` hardcoded
   `LOCK_FILE = "/tmp/trading_bot.lock"` and never read that variable. The
   live paper bot holds that lock, so the subprocess exited:

       ❌ Bot already running (PID: 1924628)
          To stop: kill 1924628

**Fix.**

- `main.py`: `LOCK_FILE = os.environ.get("LOCK_FILE_OVERRIDE") or "/tmp/trading_bot.lock"`.
  Production behaviour is byte-for-byte unchanged when the variable is unset;
  the override is opt-in and is exactly the contract the test already
  intended to rely on.
- Test: `cwd=str(Path(__file__).resolve().parents[1])`.

**Status:** FIXED (1/1).

### 5.7 Live-DB-only endpoints (3 failures)

**Root cause.** `/api/decision`, `/api/decision-history`,
`/api/actionability-summary` and `/api/cycle-candidates` each inlined
`Path(__file__).parent / "trading_bot.db"`, so the Phase A / Phase B tests
read whatever live DB sat next to the checkout. In the worktree that was a
208 KB leftover artifact whose `decision_history` table is empty — so
`ALPXR`/`WBS` were absent and the assertions could not hold.

**Fix.**

- `dashboard.py`: added one central resolver

      def _dashboard_db_path():
          override = os.environ.get("TRADING_BOT_DASHBOARD_DB")
          if override: return Path(override)
          return Path(__file__).parent / "trading_bot.db"

  and routed `api_decision`, `api_decision_history`,
  `api_actionability_summary`, `api_cycle_candidates`, `_phase_c_open_db`
  and `_p0_open_db` through it. The production default is unchanged.
- New `tests/_synthetic_dashboard_db.py` builds a deterministic synthetic DB
  (`analyzed_stocks` with ALPXR full-snapshot + WBS legacy-NULL rows,
  `decision_history`, and a `cycle_funnel` row matching the production
  schema including `not_attempted_reason` and `bot_version`).
- The Phase A and Phase B tests now point the dashboard at that synthetic DB
  via `TRADING_BOT_DASHBOARD_DB` (monkeypatched, auto-restored).

**Status:** FIXED (3/3).

## 8. Risks

1. **The P0 forensic verification is skipped in CI.** The live-DB regression
   signal is only obtained when `TRADING_BOT_DASHBOARD_DB` is pointed at the
   production DB. Mitigation: verified passing against production; the
   skip reason names the exact env var to set.
2. **Two production behaviour changes ship with this PR.**
   `POST /api/settings` (was 405 in production — the Settings UI could not
   save) and the dashboard status legend (red dot with a green-sounding
   label). Both are intentional fixes, but they are behaviour changes and are
   called out for reviewer attention.
3. **Two new opt-in environment variables**: `LOCK_FILE_OVERRIDE` and
   `TRADING_BOT_DASHBOARD_DB`. Both default to the previous behaviour when
   unset. `TRADING_BOT_DASHBOARD_DB` additionally lets an operator point the
   dashboard at a read replica.
4. **The suite no longer silently depends on a sibling checkout.** Fixing
   5.5 means the tests now genuinely cover the code under test. This can
   surface *additional* latent failures in checkouts that were previously
   masked — that is the intended behaviour, and the full suite was re-run to
   confirm it is green here.
5. The `pytest.ini` `Unknown config option: timeout` warning is pre-existing
   (`pytest-timeout` not installed) and out of scope for ENG-04b.
6. The engineering-platform test suite still hardcodes
   `/root/.openclaw/workspace/trading-bot` in several modules
   (`test_engineering_file_adapter.py`, `test_engineering_git_adapter.py`,
   `test_engineering_qa_adapter.py`, `test_engineering_registry.py`,
   `test_engineering_supervisor.py`). Those currently pass, but they are
   environment-coupled by design. §5.10 shows the pattern can hide failures;
   the remaining modules were audited and confirmed not to depend on mutable
   local artifacts. Migrating them fully is out of scope for ENG-04b and is
   recommended as follow-up work.
