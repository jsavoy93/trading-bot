## Transaction model
PRE-FLIGHT + FAIL-FAST, PARTIAL STATE POSSIBLE.

Before first write, implementation must validate input, construct ProjectConfig, validate ProjectConfig, resolve destination, calculate full planned write set, validate containment, detect all planned-file conflicts, and validate templates.

Known validation/conflict failures perform zero writes.

Unexpected write failure during apply stops immediately, does not continue remaining writes, reports written paths, reports failed target, reports partial-state condition, and does not claim rollback.

## Dry-run contract
Planning performs zero persistent writes. Plan output is bounded and structured. Per planned artifact, it includes relative destination path, action CREATE/CONFLICT, template identifier, generated byte count, generated line count, SHA-256 digest, and bounded summary. It also includes warnings, validation errors, and generated ProjectConfig. It must not return unbounded full file contents by default.

## Conflict policy
No overwrite support in Phase 1. Any planned destination file that exists is CONFLICT and causes apply to perform zero writes. No force, interactive prompt, per-file approval, or replace-if-identical behavior. Unplanned files may remain if they do not conflict.

## Destination semantics
- destination explicit
- no Path.cwd fallback
- no implicit repository discovery
- missing destination root may be created
- existing empty directory allowed
- existing non-empty directory allowed if no planned-file conflicts
- existing planned artifact is conflict and zero writes
- symlink destination root rejected
- traversal or child escape rejected
- every generated child remains inside resolved destination root

## Generic defaults and template rules
Templates must be project-agnostic. They must not include trading-bot-specific names, brokerage/trading assumptions, no_live_trading defaults, hard-coded trading-bot paths, API keys, tokens, passwords, or secret values. Generic handoff filename is `AUTONOMOUS_ENGINEERING_HANDOFF.md`. `TRADING_BOT_PROJECT` may be used only as schema/reference example.

Defaults: current schema version, caller project_id/display_name, repository_root from explicit destination, base branch configurable default `main`, governance paths to generated files, project-local workflow/event/report paths, `agents_may_merge=False`, generic prohibited operations only, QA commands/timeouts as ProjectConfig values only.

## Registry boundary
003A must not create registry JSON/YAML, serializer, registry path, project activation, or registry behavior changes. 003B owns this.

## Secrets and shell boundary
No secret values generated/requested. Environment variable names/placeholders allowed. No broad secret scanner. No arbitrary shell execution, subprocess.run, git init, git clone, gh, chmod shell, or QA execution in bootstrap implementation. Structured Python filesystem operations only.
