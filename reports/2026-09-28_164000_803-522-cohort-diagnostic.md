For the **2 CONFLICTED rows (TII, AGCO)**:
- **DIRECTLY PROVEN**: MTF disagreement (the only code path that assigns `signal_strength=CONFLICTED` in `analyze_multi_timeframe()` is `daily_signal is not None and hourly_signal is not None and daily_signal != hourly_signal`, see `src/core/smart_bot.py` line 2272).

- **DIRECTLY PERSISTED**: `timeframe_mode = multi_timeframe`, `signal = HOLD`, `signal_strength = WEAK`.
- **CODE PATHS that yield this exact persisted state in `analyze_multi_timeframe()`** (mutually exclusive):
  1. `daily_signal = BUY/SELL, hourly_signal = None` (no hourly data) → `signal = daily_signal, strength = "DAILY_ONLY"` — would NOT match (strength would be DAILY_ONLY)
  2. `daily_signal = None, hourly_signal = None` → `signal = HOLD, strength = "WEAK"` (no signal in either tf) → **MATCHES**
  3. `daily_signal = None, hourly_signal = BUY/SELL` → `signal = HOLD, strength = "WEAK"` → **MATCHES** (note: hourly_signal is `BUY` or `SELL` but daily is None — the function defaults to `signal = HOLD` here, not "use hourly")

  5. `daily_signal = BUY/SELL, hourly_signal = same` → would emit BUY/SELL, not HOLD — would NOT match
  6. Daily signal produced BUT downstream regime filter / earnings filter / trading-window / SP filter / liquidity filter / sector filter downgraded it to HOLD/WEAK → **MATCHES**

So the **510 WEAK rows** can be one of these code paths (2, 3, or 6, or combinations), and from the persisted snapshot alone we cannot distinguish them. To prove the cause we would need to either:

## 7. OWNER-FACING ANSWERS

### What exactly does SKIPPED_INVALID_DATA mean?
A row the bot persisted where `analyze_symbol()` returned `None` or threw, or where the fallback HOLD-score path short-circuited (NaN indicator, `score_components` returned None, outer exception). **No strategy-gate evaluation ran.** It is an observability marker ensuring `analyzed_count == decision_history rows` (the OBS-002 invariant). Not an error count — it's the bot's way of recording that it couldn't make a real decision.

### Within the apparent RSI+SMA joint-pass cohort, why did the invalid subset become invalid?
All 786 invalid rows came from the SAME path: `analyze_symbol()` returned None → fallback HOLD-score was computed and saved → `_persist_skipped_terminal_decision(outcome="SKIPPED_INVALID_DATA")` was called. The fallback computed real RSI/SMA values (which is why the joint-pass filter matched them), but no strategy-gate evaluation occurred, so no MACD/volume gate rows were persisted.

### Are those invalid rows legitimate RSI+SMA opportunities, or persistence artifacts/partial analyses?
**Partial analyses / fallback artifacts.** They are NOT legitimate BUY opportunities. The RSI/SMA values are real, but no MACD, no volume, and no actual `buy_eligible` evaluation happened. They appeared in joint-pass because the dashboard's filter is purely structural (gate-row presence + passed=1) and doesn't distinguish a real strategy evaluation from a fallback HOLD computation.

### How many unique symbols make up the invalid subset?
**126 unique symbols.** Median 8 cycles per symbol; max 12. The bot continuously re-evaluates the same symbols (analyzed every ~5 minutes in continuous mode).

### What exactly does HOLD_INELIGIBLE mean?
A row where the bot completed real analysis (RSI, SMA, and (for non-MTF path) MACD/volume were evaluated) and the result was a non-actionable HOLD. `decision.outcome = HOLD_INELIGIBLE` is the catch-all for any non-actionable analysis in `_build_decision_snapshot` line 1664. Score is real (not `score_invalid_data`).

### Within the valid joint-pass cohort, why did the HOLD subset not become BUY?
All 512 are `multi_timeframe` analysis paths. None of them met the MTF agreement requirement to emit BUY (or SELL). 510 of them ended with `signal_strength=WEAK`; 2 ended with `signal_strength=CONFLICTED`. The MTF path's BUY emission requires BOTH daily_signal == BUY AND hourly_signal == BUY.

### Is MTF disagreement proven, inferred, or not reconstructable?
- **2 CONFLICTED rows**: PROVEN MTF disagreement (the only code path that yields CONFLICTED in MTF mode is `daily_signal != hourly_signal` when both are non-None).
- **510 WEAK rows**: NOT UNIQUELY RECONSTRUCTABLE. Multiple code branches can produce `WEAK` in MTF mode (no daily BUY, no hourly data, downstream filter downgrade, etc.). The honest label is "MTF no actionable signal" — not "MTF disagreement".
- The dashboard's `hold_reason_buckets.MTF_DISAGREEMENT = 522` label overstates the WEAK population. It is correct for the 2 CONFLICTED rows but misleading for the 510 WEAK rows.

### Are MACD or volume demonstrably blocking these rows?
**No.** For all 512 rows, MACD and volume gate rows are absent from `decision_gate_evaluations`:
- The MTF analysis path does not call `buy_eligible` (the expression that checks MACD > 0 and volume ≥ 1.0).
- The MTF path's analysis_result dict lacks the `macd_histogram` key, so the gate row is never created.
- Even if MACD/volume had been evaluated, volume is NOT currently required (`enable_volume_confirmation = False` in persisted settings).
- The actual reason these rows didn't become BUY is upstream of MACD/volume: the MTF agreement check failed (no daily BUY OR no hourly BUY OR disagreement).

### What information is missing from persistence that prevents a definitive explanation?
The most impactful missing fields are:
1. **`daily_signal`** — directly persisted would let us distinguish "no daily BUY" from "no hourly".
2. **`hourly_signal`** — directly persisted would let us distinguish "no hourly" from "hourly disagreed".
3. **`mtf_conflict_blocked`**, **`daily_only`**, **`volume_downgrade`**, **`volume_confirmed`** — these are computed in `analyze_multi_timeframe()` but not written to the snapshot.
4. **`macd_histogram` in MTF analysis_result** — would let `_build_decision_snapshot` create a `macd_positive` gate row for MTF rows, closing the observability gap.

### What ONE observability improvement would most improve future diagnosis?
**Persisting `daily_signal` and `hourly_signal` (and the boolean flags `mtf_conflict_blocked`, `daily_only`) in `strategy_eligibility` or a new top-level field in the snapshot.** This would let the dashboard distinguish "MTF disagreement" (2/512) from "no daily BUY" / "no hourly data" (510/512) without re-running analysis. It's a one-line addition in `analyze_multi_timeframe()` and a `_build_decision_snapshot` field.

### Do NOT recommend loosening the strategy.
Not recommending any threshold change. The 512 valid HOLDs and 786 invalid fallbacks are not caused by over-tight thresholds; they are caused by the MTF no-action condition (no daily BUY) and the fallback HOLD path (analyze_symbol None), respectively.
