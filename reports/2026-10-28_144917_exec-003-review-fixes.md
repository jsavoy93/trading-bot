## Step 1 — Defect (a): unresolved broker outcomes left no durable audit event

### Root cause at ce6b92a
`poll_order_fills()` (`src/core/smart_bot.py`) counted unresolved outcomes in an
in-memory `summary` and then `continue`d on `if not result["changed"]` BEFORE any
persistence call. `update_trade_lifecycle()` — the only writer of `order_events` —
was therefore never reached for:
- a broker fetch failure (network error → `broker_event = None`),
- an unrecognized broker status (`reconcile()` returns `changed=False, unresolved=True`),
- a reconcile exception (bare `continue`).

### Fix
1. `src/database/sqlite_db.py` — NEW `SQLiteDB.record_order_event(trade_id,
   broker_order_id, raw_status, note, unresolved=True)`:
   - append-only: a single `INSERT INTO order_events`, **never** an `UPDATE`
     against `trades` (status / filled_qty / avg_fill_price / order_updated_at are
     untouched);
   - `unresolved=True` records `canonical_status='UNRESOLVED'` and `unresolved = 1`;
   - honors `TRADING_BOT_TESTING_FATAL_PERSISTENCE=1` (raise instead of swallow);
   - never fabricates a state.
2. `src/core/smart_bot.py` — NEW module-level helper `_record_unresolved_event(db,
   row, broker_order_id, raw_status, note)` (module-level on purpose: the poller is
   exercised with stand-in objects in tests, and `self.<helper>` would couple the
   bookkeeping contract to a concrete `SmartTradingBot` instance).
3. `poll_order_fills()` now calls that helper on ALL THREE unresolved paths:
   reconcile exception, unresolved broker status, broker fetch failure. An
   unresolved outcome `continue`s — it never mutates lifecycle state — so exactly
   ONE `order_events` row is written per unresolved poll.

## Step 2 — Defect (b): out-of-order statuses regressed lifecycle state; late fill evidence was unreachable

### Root cause at ce6b92a
- `reconcile()` computed `effective_status` from the broker event, then only
  rejected a LOWER-rank event when the quantity did NOT advance. An out-of-order
  `ACCEPTED` that carried a higher filled_qty therefore REGRESSED a
  `PARTIALLY_FILLED` row back to `ACCEPTED`.
- `get_pending_fill_trades()` excluded every terminal status, so a
  `CANCELED`/`EXPIRED` order that later reported a fill (cancel-vs-fill race,
  which `reconcile()` explicitly handles) was never re-polled in production —
  legitimate delayed fill evidence was unreachable.

### Fix
1. `src/core/order_lifecycle.py` — `reconcile()`:
   - **Elevation on quantity advance**: if `filled_qty` advances on a NON-terminal
     row and the event status ranks below `PARTIALLY_FILLED`, the status becomes
     `PARTIALLY_FILLED` — or `FILLED` when the quantity is complete
     (`filled_qty >= ordered_qty`, which the module contract already sanctions as
     broker-reported fill evidence). This directly fixes
     `PARTIALLY_FILLED(4/10) + ACCEPTED(6) → PARTIALLY_FILLED 6`.
   - **Late fill evidence on CANCELED/EXPIRED**: within the terminal-state guard,
     a CANCELED/EXPIRED row whose cumulative quantity ADVANCES now advances
     `filled_qty` / `avg_fill_price` and KEEPS its terminal status. A stale event
     (no advance) still changes nothing.
2. `src/database/sqlite_db.py` — `get_pending_fill_trades()`:
   - `REPOLL_STATUSES = ("CANCELED", "EXPIRED")`, `REPOLL_HORIZON_HOURS = 24`;
   - CANCELED/EXPIRED rows are re-polled while
     `julianday(COALESCE(order_updated_at, created_at)) >= julianday('now','-24 hours')`;
   - FILLED / REJECTED remain final and are never re-polled.

## Step 3 — Defect (c): follow-up tranches bypassed the ledger

### Root cause at ce6b92a
`_execute_pending_entry_tranches()` called `submit_order()` and then set
`tranche['status'] = 'filled'` in memory. No `log_trade` call, no `broker_order_id`
persisted → tranche 2/3 orders were invisible to `poll_order_fills()` and were
mislabeled as filled at submission time. (Reachable in the current config: the only
gate is `quantity >= 3` in `execute_trade`.)

### Fix
1. `_execute_pending_entry_tranches()` now persists every tranche submission via
   `log_trade` through the module-level helper `_persist_tranche_submission(...)`:
   status `SUBMITTED`, `broker_order_id`, `qty`, `price`, `rsi`, `pnl = None`,
   `notes = "EXEC-003 entry tranche N (trigger=...)"`.
2. The in-memory tranche status is now `'submitted'` — never `'filled'` at
   submission time. `check_tranche_triggers()` only fires tranches whose status is
   `'pending'`, so a submitted tranche is NOT re-submitted (proven by test `c2`).
3. `trades.notes` — NEW additive nullable column (idempotent `ALTER TABLE`, same
   pattern as `filled_qty` / `avg_fill_price` / `order_updated_at`).
4. NOT changed (out of authorized scope): stop-loss path, portfolio-order path,
   tranche 1's in-memory label in `execute_trade`, tranche 2/3 risk guards.
