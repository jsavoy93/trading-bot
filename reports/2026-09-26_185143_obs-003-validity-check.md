## 2. Root causes of MISSING_DECISION_BAR

**Total: 69,925 / 91,138 decisions (76.7 %) are MISSING_DECISION_BAR.**

This is the headline coverage question. Three independent causes:

### Cause A - Decision time is outside Alpaca paper-tier bar coverage (the dominant cause)

Alpaca paper-tier historical 1-minute bars for liquid US names start at
~08:00 UTC (04:00 ET pre-market open) and run through ~23:59 UTC. They do
**not** cover the overnight window 00:00-08:00 UTC. SmartBot evaluates
symbols every ~85 minutes around the clock, so a large fraction of
decisions fire during the uncovered overnight window.

| session (UTC) | decisions | MISSING | % missing |
|---------------|----------:|--------:|----------:|
| 00:00-07:59 (closed_overnight) | 43,612 | 43,612 | 100.00% |
| 08:00-13:29 (pre_market) | 29,826 | 22,754 | 76.29% |
| 13:30-19:59 (regular_dst) | 17,070 | 3,445 | 20.18% |
| 20:00-23:59 (after_hours) | 630 | 114 | 18.10% |

100% of closed_overnight decisions are missing because no 1-min bar
exists at-or-before cycle_start in the Alpaca paper-tier cache. The 76%
pre-market missing rate is because pre-market decisions that fire **before
the first bar in the cache** for a given symbol/date cannot find a
decision-time bar.

### Cause B - Symbol has no Alpaca paper-tier data at all

914 / 13,522 unique symbols (6.76 %) have cache files but every file is
empty (Alpaca returned no rows). These are OTC / pink-sheet / warrant /
inactive ticker symbols for which paper-tier returns nothing.

6,008 / 91,138 decisions (6.59 %) belong to this set.

### Cause C - Symbol has data on other dates but not on this specific decision date

1,351 unique symbols (9.99 %) have cache files for some dates but not
the decision's date. 4,112 / 91,138 decisions (4.51 %) are in this
category.

### Cause D - No cache file at all

4 decisions / 91,138 (0.00 %) have no cache file. One symbol
(`UNKNOWN_SINGLE`) is missing entirely. Negligible.

### Cause E - Decision_time matches a gap inside the available cache

Some symbols (low-volume ETFs, e.g. JDIV, JULJ, CLOC) only have a few
scattered bars per day, often late in the session. Decisions that fire
before the first bar of the day on those symbols correctly produce
MISSING_DECISION_BAR even during regular session. This is a sub-case of
Cause A (Alpaca data quality) but worth noting separately.

**Summary:** the 76.7 % MISSING_DECISION_BAR rate is overwhelmingly
explained by Alpaca paper-tier not returning 1-minute bars outside the
extended-hours window (08:00-23:59 UTC), not by a labeling defect.

## 3. Implementation defect check

### Cache date coverage ✓
For every MISSING_HAS_BARS decision in the sample, the cache file for
its (symbol, decision_date) exists and contains bars. The decision is
correctly marked MISSING because cycle_start is **before** the first
bar in the merged frame. Spot-checked 10 decisions across closed_overnight,
pre_market, and regular_dst hours. All correctly handled.

### UTC conversion ✓
`cycle_start` is parsed via `pd.to_datetime(..., utc=True)`. Bar index
is tz-localized to UTC if missing. The merged frame uses
`tz_convert("UTC").date` for date extraction. Verified by spot checks.

### At-or-before rule ✓
`decision_bar()` uses `idx[idx <= cycle_start]` - last bar with index
≤ cycle_start. Confirmed by 4 dedicated unit tests + spot checks on real
decisions.

### Empty-cache files correspond to genuine empty Alpaca responses ✓
The `EMPTY_ALL` classification (4,831 cache files, 321 bytes each) was
verified by loading a sample - they are `pd.DataFrame()` empty frames
that `_save_to_disk` writes when `client.get_stock_bars()` returns an
empty MultiIndex. The 321-byte pickle size is the empty-DataFrame pickle
header. 36365 non-empty files have sizes from 1 KB to 62 KB.

### Cache symbol/date mapping ✓
Cache files use `{symbol}_{YYYY-MM-DD}.pkl` with the symbol part
preserving any underscores. `_cache_path()` uses `safe_sym.replace("/",
"_")` defensively. Spot-checked: every MISSING decision's
`(symbol, date_str)` cache file exists when expected.

### Successfully returned bars reach the labeler ✓
Spot-checked 5 OK decisions - for each, `decision_price_ts` falls in the
merged frame, `decision_price` is the at-or-before bar's close, and the
forward price is computed correctly.

### **DST session-window defect FOUND and FIXED**

**Defect:** `price_alignment.py` defined `SESSION_OPEN = time(14, 30)`
and `SESSION_CLOSE = time(21, 00)`, claiming these were DST-equivalent
UTC times. They are NOT - they are **standard-time** UTC times. With DST
in effect (March 8 - November 1, 2026; ET = UTC-4), the actual US
regular session is **13:30-20:00 UTC**.

**Impact:**
- `is_regular_session_minute()` accepted the 20:00-21:00 UTC after-hours
  window as "regular session" for late-September 2026 dates.
- `forward_bar_trading_minutes()` walking past 20:00 UTC counted
  after-hours minutes as "trading minutes".
- 23,093 of 36,365 (63.5 %) cache files contain bars in 20:00-20:59 UTC.
  All of these would have been (and were, in the f28aea1 run) mis-stepped
  during the trading-minute walk.
- Late-day decisions (cycle_start ≥ ~19:30 UTC) had their +30m/+60m/+240m
  forward prices pulled from after-hours territory, where prices are
  effectively static.

**Fix:** updated `SESSION_OPEN = time(13, 30)` and
`SESSION_CLOSE = time(20, 0)` in `src/research/price_alignment.py`. Added
explicit DST-aware comment explaining why these are the correct UTC
times for the OBS-003 cohort. Added new regression test
`TestRegularSessionFilter::test_dst_session_window_documented` that
asserts `SESSION_OPEN == time(13, 30)` and `SESSION_CLOSE == time(20, 0)`.

**Qualitative findings were stable across the fix** (see Section 8). The
DST bug did not invert any prior finding; it only tightened or
moderated some magnitudes.

| A. joint-pass | 4,614 | **49.67 %** | 34.53 % | 15.80 % |

| C. rsi_fail_sma_pass | 23,096 | 7.03 % | 80.46 % | 12.50 % |
| D. both fail | 32,698 | 3.89 % | 86.27 % | 9.84 % |

**This is the most important finding of the validity check.**

The four gate groups are **NOT being sampled at the same rate from the
underlying Alpaca data**. The joint-pass cohort (Group A) is heavily
concentrated in symbols with EMPTY_ALL cache status (49.67 % vs ≤ 7 %
for the other three groups). After applying the gates, the "would-have-
bought" subset is **systematically drawn from a population with much
less Alpaca data availability**.

Why? Likely because the joint-pass combination (RSI ≤ 35 AND SMA fast
above slow) is more common in less-liquid / OTC / warrant / inactive
tickers where price-velocity patterns produce both conditions
simultaneously. The 137-169 successfully-labeled joint-pass decisions
that DO get returned prices are a **biased sub-subset** of the joint-pass
population.

## 11. Validity classification

### Classification: **USABLE WITH MATERIAL COVERAGE LIMITATION**

The OBS-003 retrospective evidence is **usable for hypothesis generation**
but not for **strategy decisions**. Specifically:

**USABLE FOR HYPOTHESIS GENERATION:**
- Joint-pass cohort is consistently underwater across all four horizons
  (raw and dedup). The pattern is qualitatively robust.
- High-RSI cohort is consistently strongly positive across all four
  horizons (raw and dedup). The pattern is qualitatively robust.
- The DST fix did not change any qualitative direction; magnitudes
  tightened modestly.
- Coverage limitation is real but explainable (Alpaca paper-tier does
  not cover 00:00-08:00 UTC).

**MATERIAL COVERAGE LIMITATION:**
- Only 12-23 % coverage overall (depending on horizon), so the labeled
  subset is ~13-22K decisions out of 91K.
- Joint-pass cohort has only 169-394 OK labels per horizon - small and
  drawn from a sub-population where 50 % of decisions are on EMPTY_ALL
  symbols.
- The bias is **systematic**: gate groups are NOT sampled equally from
  the symbol universe. Group A is heavily skewed toward thinly-traded
  names where Alpaca paper-tier has no or minimal data.
- One labeled population (SELL_BLOCKED_DYNAMIC, 293 obs, 97.6 %
  MISSING) is almost entirely unobservable in forward-return terms.

**NOT YET USABLE (without further work):**
- Any claim about realized P&L (trades table is empty).
- Any claim about live trading performance.
- Any claim about whether relaxing RSI/SMA thresholds would have been
  profitable.
- Any claim that "the strategy has no edge" (coverage is too low to
  establish that).

**Recommendations for future observation:**
1. Collect live forward-return data over a longer window (until the
   paper-tier lag clears for newer decisions).
2. Restrict analysis to regular_dst session only when comparing cohorts.
3. Stratify by symbol-cache-class to avoid the Group A / EMPTY_ALL bias.
4. Investigate why SELL decisions have such low coverage.

## 14. Final question

**"If we stop here, is the current evidence strong enough to FORM a
strategy hypothesis, even though it is not strong enough to CHANGE the
strategy?"**

**Answer: yes - for one specific, narrow, testable hypothesis.**

The two qualitative findings are robust to:
- the DST fix,
- raw vs dedup (30-min spacing),
- market-session breakdown (regular_dst subset alone shows the same
  pattern at smaller sample sizes).

The hypothesis the evidence supports:

> *"In the OBS-003 cohort (2026-09-23..24 v1 decisions), observations
> that satisfied BOTH the RSI(≤35) and SMA(uptrend) gates were
> followed by negative median forward returns at all intraday horizons.
> Conversely, observations with RSI substantially above the threshold
> (≥ +20 points) were followed by strongly positive forward returns."*

This is **not** a strategy recommendation. It does not survive
generalization (single 17-hour window, single market regime, paper-tier
data only). It does not establish edge. It does not justify any change.

But it does justify:
- A larger-window retrospective (multi-week or multi-month).
- A live forward-return collection to confirm or refute in real time.
- An investigation of whether the gates are systematically
  over-permissive for thinly-traded symbols.

**Stopping here is appropriate.** No implementation should follow
without explicit owner authorization of a follow-on task.
