## 5. Known risks / uncertainties

1. **Cancel polling is bounded.** `_ensure_canceled` polls up to `CANCEL_POLL_ATTEMPTS=4` with `CANCEL_POLL_SLEEP_S=2.0` (≈8 s). If Alpaca keeps the order in `pending_cancel` longer, the run sends **no** market sell and the trade is retried next run — the stop stays in place (never naked). This is deliberate, per Josh's instruction.
2. **A trade whose stop can never be confirmed canceled will repeat every run.** It is logged as `exit_error` with `unconfirmed`; a human must clear it. There is no auto-escalation.
3. **`pending_cancel` polling uses a blocking sleep inside the run** (max ≈8 s per stuck order). With few trades this is acceptable; it is not parallelised.
4. **The replace label `-stop-r<k>` grows with the number of raises** (one raise per run at most). At `k` ≥ 100 the label would exceed the 48-char Alpaca limit; `make_stop_replace_client_order_id` raises `ValueError` before that, and the raise is caught per symbol. Practically unreachable (a 15-day max holding ⇒ ≤ 15 raises).
5. **The C4 ref-date skip is best-effort around holidays.** `last_completed_trading_day` is weekday-based; a market holiday yields the prior weekday, and the C4 `ref_date` match then finds nothing. That is the safe direction (the skip simply does not fire).
6. **`STRAT_SWING_C4_DB` / `--c4-db` still points at the `/root/strat-swing` C4 shadow DB.** That checkout was NOT touched by this task (per instruction); the DB path was only read by the test fixtures, which are hermetic temp copies.
7. **The fake broker models Alpaca's replace/cancel semantics, not Alpaca itself.** The PATCH payload `{stop_price, client_order_id}` is accepted by Alpaca for a stop order; a live paper dry-run is still the only way to prove the exact wire format end to end.
