# OPS-017 — Add bounded OPS-015 launcher and manual smoke setup

## Objective

Make the merged OPS-015 Telegram adapter safely runnable for a bounded manual
smoke test. Define and validate external secret handling, add a supported
launcher, expose structured secret-safe runtime diagnostics, detect competing
pollers, return deterministic failure exit codes, and record real-bot smoke
evidence. Do not install or operate a background service.

## Priority

P1

## Owner

trading-manager

## Exact acceptance criteria

1. Runtime configuration uses exactly
   `ENGINEERING_TELEGRAM_BOT_TOKEN` and
   `ENGINEERING_TELEGRAM_JOSH_CHAT_ID`. Real values exist only in
   `/etc/trading-bot/ops-015.env`, outside Git, with mode `0600`, owned by the
   invoking operator, and are never requested in chat, committed, printed,
   logged, persisted, included in reports, or passed as command-line values.
2. A repository-owned launcher provides the exact supported command
   `.venv/bin/python -m engineering.telegram_service --env-file
   /etc/trading-bot/ops-015.env --smoke --event-store
   .agent-state/telegram-smoke-events.sqlite3 --max-polls 20 --max-seconds
   300`. It validates the environment file, repository paths, both finite
   bounds, fixed Telegram origin, and exact isolated smoke event-store path
   before making a network request.
3. Smoke mode is foreground-only, uses Telegram long polling, performs at most
   20 polls and runs at most 300 elapsed seconds, stopping when either bound is
   reached. It handles `SIGINT`/`SIGTERM` with graceful lease release, never
   daemonizes, never polls endlessly, never restarts automatically, and never
   installs, starts, enables, or modifies a service.
4. Before the real smoke test, an operator verifies that Josh initiated a
   private chat and that the observed `message.chat.id` and `message.from.id`
   are identical to the configured positive numeric allowlist. The token and
   inbound message text are not displayed as evidence.
5. The approved Josh private chat receives deterministic bounded responses for
   `/status`, `/current`, and `/report`; exact observed responses are recorded
   with secret-free state context. No other read command, raw report, log,
   artifact, file, environment value, or unbounded output is exposed.
6. An unauthorized second Telegram account receives no response. Exactly one
   sanitized `telegram.access_denied` audit event is verified in the isolated
   `.agent-state/telegram-smoke-events.sqlite3` store, and neither the
   unauthorized ID nor inbound content is persisted or logged. The normal
   `.agent-state/engineering-events.sqlite3` database is never opened, created,
   read, or modified by smoke mode.
7. `/pause` and `/resume` are exercised only through
   `EngineeringControlService`; the smoke record proves revisioned idempotent
   state changes and corresponding `manager.paused` and `manager.resumed`
   events in the isolated smoke store. The isolated manager pause record is
   restored to its exact pre-smoke state during cleanup, including when either
   the poll or elapsed-time bound ends the run; the normal engineering manager
   event/control database remains untouched.
8. The launcher emits bounded one-line structured JSON logs to stderr for
   startup, configuration validation, poll lifecycle, authorized command type,
   denied access, delivery retry/dead-letter summary, shutdown, and terminal
   outcome. Logs use an explicit field allowlist and never contain tokens,
   chat/sender IDs, message text, query payloads, exceptions with request URLs,
   or raw Telegram responses.
9. A competing consumer lease fails closed before polling and exits with code
   `3`. A permanent Telegram transport error is distinguishable from a normal
   bounded smoke completion and exits with code `4`; configuration errors exit
   `2`, runtime/store failures exit `5`, graceful success exits `0`, and signal
   interruption follows the documented shell convention. Transient errors
   retain bounded retry/backoff behavior.
10. Automated tests use fake Telegram transport, query/control boundaries,
    clocks, signals, and sleepers and make no external request. After focused
    tests and the full safe suite pass, the separately approved real smoke test
    verifies the full ordered sequence `/status`, `/current`, `/report`,
    `/pause`, repeated `/pause`, `/resume`, and unauthorized `/status`. Cleanup
    stops the launcher, releases or expires leases, restores the pre-smoke
    isolated pause state even at either bound, preserves auditable state,
    removes no file without Josh's approval, and documents token revocation
    plus branch/commit rollback procedures.

## Required secret names and storage

The only secret/runtime identity names are:

- `ENGINEERING_TELEGRAM_BOT_TOKEN`
- `ENGINEERING_TELEGRAM_JOSH_CHAT_ID`

The approved external storage candidate is:

```text
/etc/trading-bot/ops-015.env
```

The file must be outside the repository, regular rather than a symlink, mode
`0600`, and owned by the invoking operator. It contains exactly the two keys,
one per line. The implementation must reject extra keys, duplicate keys,
shell syntax, substitutions, malformed IDs, whitespace-bearing tokens, unsafe
ownership, and broader permissions. Tests use temporary fake files and values;
the real file is created only during a separately approved setup action.

## Safe launcher contract

The supported bounded smoke command will be:

```text
.venv/bin/python -m engineering.telegram_service --env-file /etc/trading-bot/ops-015.env --smoke --event-store .agent-state/telegram-smoke-events.sqlite3 --max-polls 20 --max-seconds 300
```

The launcher must construct only `TelegramHTTPTransport`, the isolated
`EngineeringEventStore`, `WorkflowStore`, `EngineeringQueryService`,
`EngineeringControlService`, and `TelegramEngineeringAdapter`. It must not
construct trading or brokerage services. It must expose no general command,
module, path, URL, Python expression, or arbitrary environment override.
`--event-store` accepts only the exact smoke path shown above. Smoke mode must
refuse the normal `.agent-state/engineering-events.sqlite3` path and must not
open, create, read, migrate, lock, or modify that normal database.

Both bounds are mandatory and independently enforced using injected clocks:
the launcher stops before poll 21 or when monotonic elapsed time reaches 300
seconds, whichever occurs first. Bound handling runs the same `finally`
cleanup as signals and failures. The launcher remains a single foreground
process with no daemonization, backgrounding, endless loop, supervisor, or
automatic restart behavior.

## Manual smoke-test sequence

1. Confirm no existing adapter or `getUpdates` consumer is active.
2. Record the pre-smoke manager pause revision/state and denied-event count
   without exposing identities or message content.
3. Josh opens a private chat with the new bot and sends `/status`.
4. Verify the private chat and sender IDs match the configured allowlist without
   printing them into the report.
5. Run the exact bounded smoke command in the foreground.
6. From Josh's account, exercise `/status`, `/current`, then `/report` and record
   the exact bounded responses.
7. Exercise `/pause`, repeat `/pause` to prove idempotency, then `/resume`; prove
   revision and audit-event behavior in the isolated smoke store.
8. From a second account, send unauthorized `/status`; require no response and
   exactly one sanitized denial event.
9. Require all seven interactions to complete before the first of 20 polls or
   300 elapsed seconds. If either bound arrives first, stop, mark the smoke
   incomplete, and run cleanup; never extend or restart automatically.
10. Verify the isolated pause state was restored and the normal engineering
    event database was not accessed or modified, then inspect only structured
    logs and bounded smoke-database projections and record cleanup.

The real smoke test is a controlled external action. It requires Josh's
separate approval after implementation tests pass and must never run in pytest.

## Structured runtime logging

- Emit newline-delimited JSON to stderr; stdout is reserved for one bounded
  terminal summary if needed.
- Required fields: schema version, UTC timestamp, severity, component, event,
  worker ID, poll count, bounded delivery status, exit code, and sanitized
  reason code.
- Prohibited fields: token, chat/sender ID, message text, command arguments,
  URL, environment, raw payload/response, traceback containing a tokenized URL,
  report body, or arbitrary exception text.
- Logging failure must not weaken allowlisting or cause raw exceptions to be
  printed; the launcher exits with the documented runtime failure code.

## Failure and exit-code contract

| Code | Meaning |
|---:|---|
| `0` | Bounded smoke completed successfully |
| `2` | Invalid/missing secret file, credentials, arguments, or startup configuration |
| `3` | Competing poller/consumer lease detected |
| `4` | Permanent Telegram authentication, protocol, or transport rejection |
| `5` | Event store, workflow/query/control, logging, or unexpected runtime failure |
| `130` | Operator interruption by `SIGINT`; graceful cleanup attempted |
| `143` | Termination by `SIGTERM`; graceful cleanup attempted |

Transient Telegram failures remain bounded and retry according to OPS-015. The
launcher stops when either 20 polls or 300 monotonic seconds is reached. A
bound-ended run returns `0` only if the complete required interaction sequence
passed and pause restoration, lease release, and other cleanup succeeded;
otherwise it returns the bounded runtime failure code `5`. It never restarts
itself.

## Cleanup and rollback

- Stop the foreground launcher and verify the Telegram consumer lease is
  released or reaches its finite expiry.
- In an unconditional `finally` path, restore the exact pre-smoke pause state in
  `.agent-state/telegram-smoke-events.sqlite3` through
  `EngineeringControlService`, preserving its audit trail. This restoration is
  mandatory on success, failure, signal, competing-poller detection, poll-limit
  completion, and elapsed-time-limit completion.
- Verify `.agent-state/engineering-events.sqlite3` was not opened or modified.
- Do not delete or rewrite the isolated smoke event database; preserve evidence.
- Revoke and rotate the bot token through verified `@BotFather` if it was
  exposed. Updating or removing the external secret file requires Josh's
  explicit setup/cleanup approval.
- Code rollback is branch/commit based: stop the launcher, do not merge the
  feature PR, or revert the eventual merge through a separately reviewed PR.
- No cleanup step deletes repository files, edits Git history, touches
  `trading_bot.db`, changes trading state, or disables unrelated processes.

## Security constraints

- Default deny remains exact: both chat and sender ID must match Josh's positive
  numeric ID and the chat must be private and not forwarded.
- Never display, echo, persist, log, report, or place the token/chat ID in a
  process argument, Git content, traceback, URL diagnostic, or command history.
- Only the fixed Telegram HTTPS origin is allowed; no configurable host or
  proxy bypass is introduced.
- The launcher is foreground, finite, single-task, and incapable of daemonizing
  or launching another process. It stops at 20 polls or 300 seconds, whichever
  occurs first, and has no endless polling or automatic restart path.
- Smoke mode is isolated from `.agent-state/engineering-events.sqlite3`; path
  validation must reject the normal database and aliases resolving to it.
- No shell, Git, GitHub, Codex, agent, brokerage, trading, file-browser,
  deployment, approval, or arbitrary command capability.
- Manual smoke evidence is bounded and sanitized; real inbound content and
  identities are never copied into repository reports.
- Secret-file creation and real Telegram I/O require an explicit operational
  approval separate from proposal and implementation approval.

## Focused tests

- Secret file: missing, wrong type, symlink, permissions, owner, duplicate or
  unknown keys, shell syntax, malformed token/ID, and secret-canary redaction.
- CLI: exact accepted command, rejected extra arguments/modes/paths, finite poll
  and elapsed-time bounds, exact isolated smoke path, rejection of the normal
  event database and path aliases, and no trading/brokerage construction.
- Bounds: stop before poll 21, stop at 300 monotonic seconds, stop on whichever
  bound occurs first, never auto-restart, and never perform an extra poll after
  either bound.
- Signals: bounded foreground completion, `SIGINT`, `SIGTERM`, lease release,
  pre-smoke pause-state restoration on both bounds and every terminal path, and
  cleanup failures.
- Logging: exact JSON schema, bounded fields/order, secret/identity/message/URL
  canaries absent from every level and exception path.
- Outcomes: authorized commands, unauthorized denial, duplicate update,
  competing poller exit `3`, permanent transport exit `4`, config exit `2`,
  runtime exit `5`, success `0`, transient retry/backoff, and dead letters.
- Full sequence: `/status`, `/current`, `/report`, `/pause`, repeated `/pause`,
  `/resume`, and unauthorized `/status` must all be observed before a smoke run
  can pass.
- Isolation: normal event-database open/connect/mtime canaries prove smoke mode
  neither reads nor modifies `.agent-state/engineering-events.sqlite3`.
- Boundary isolation: fake Telegram/query/control/store/clocks/signals/sleepers;
  fail if a real network, subprocess, shell, Git, Codex, brokerage, trading, or
  service-manager boundary is invoked.

## Known risks

- The real smoke test is an external state change and can consume pending
  updates; it must not overlap another poller.
- Telegram token or Josh-account compromise remains a control-channel risk.
- Secret-file permission checks reduce but cannot eliminate host-root access.
- Structured logs can leak through unexpected exception text unless every
  boundary maps failures to fixed reason codes.
- Signal cleanup may fail after a hard kill; finite lease expiry is the fallback.
- SQLite lease coordination is single-host and clock-sensitive.
- Testing `/pause` can temporarily stop manager dispatch; exact state restoration
  and audit verification are mandatory.
- A bounded foreground launcher is not availability management. Without
  systemd or another separately approved supervisor, it stops after smoke mode.
