# OPS-015 — Add allowlisted Telegram engineering adapter

## Objective

Add a standalone Telegram adapter that consumes the OPS-014 durable event and
outbox contract, sends bounded engineering notifications, exposes a small
allowlisted command surface, and communicates only through deterministic
engineering query/control services. It must never control the interactive
Codex TUI or trading bot directly.

## Priority

P1

## Owner

trading-manager

## Exact acceptance criteria

1. A standalone adapter uses Telegram Bot API long polling with finite
   connect/read timeouts, finite exponential backoff, persisted update offset,
   graceful shutdown, and a one-process consumer lease.
2. Only the configured Josh chat ID and matching private-chat sender ID are
   accepted; every other chat, sender, forwarded message, channel post, and
   group message is denied and security-audited without echoing its content.
3. Task completion, failure, blocked, stale, PR-ready, and approval-required
   events are delivered from the OPS-014 outbox with idempotent delivery
   records, bounded retries, and dead-letter behavior.
4. `/status`, `/current`, `/next`, and `/report` read only from
   `EngineeringQueryService` and return deterministic, bounded, sanitized
   responses.
5. `/pause` and `/resume` modify only the revisioned deterministic engineering
   manager pause flag through a narrow control service, are idempotent, emit
   audited events, and never signal processes or affect the trading bot.
6. Unknown, malformed, or oversized commands return bounded help or rejection;
   command length, arguments, update batches, response size, retries, polling
   duration, and rate are strictly bounded.
7. The Telegram bot token and allowlisted identity come from environment or an
   injected runtime provider and are never persisted in events, logs, reports,
   exceptions, test snapshots, or Telegram responses.
8. The adapter never imports or invokes interactive Codex, launches agents,
   reads raw stdout/stderr artifacts, executes shell or Git commands, merges,
   pushes, deploys, or changes trading settings.
9. All tests use fake Telegram transport, query service, control service,
   clocks, and sleepers; tests make no network call and require no real token.
10. Focused Telegram/control/event tests pass, followed by the complete safe
    suite with the existing live-brokerage test gate intact.

## Security constraints

- Default deny with exact numeric allowlist; require both chat and sender ID and
  a private chat.
- Token-safe structured logging with explicit secret canaries and redaction.
- Use only the fixed HTTPS Telegram Bot API origin; reject configurable
  arbitrary endpoints outside injected tests.
- Persist only bounded update/message receipt metadata, never arbitrary inbound
  message bodies.
- Cap Telegram output below the platform message limit and paginate through
  deterministic commands rather than forwarding raw reports.
- `/pause` and `/resume` control manager dispatch only. They are not approval,
  merge, deployment, process-control, or trading commands.
- No shell, Git, brokerage, Codex, file-browser, or raw-artifact capability.

## Implementation sequence

1. Confirm OPS-014 is merged and its event/query contracts are stable.
2. Add a transport protocol plus fake transport, bounded polling, and response
   models without starting a service.
3. Add allowlist validation, command parser, and safe response renderer.
4. Implement `/status`, `/current`, `/next`, and `/report` over the shared query
   service.
5. Add the outbox delivery worker with consumer lease, offset persistence,
   bounded retry/backoff, and dead-letter behavior.
6. Add the narrow manager pause/resume control service and corresponding events.
7. Run focused tests, security/adversarial tests, and the full safe suite.
8. Stop for Josh's review; do not install or deploy a long-running service.

## Focused tests

- Authorized/unauthorized combinations for chat ID, sender ID, chat type,
  forwards, groups, and channels.
- Missing token/allowlist fail-closed startup without secret disclosure.
- Long-poll timeout, graceful cancellation, update-offset persistence, restart,
  duplicate update, duplicate event, and one-consumer lease behavior.
- Telegram 429 `retry_after`, transient failure, permanent failure, attempt cap,
  and dead-letter tests with fake clocks/sleepers.
- Every command in active, inactive, failed, blocked, stale, report-ready, and
  missing-evidence states.
- Empty, malformed, unknown, injected, and oversized command cases.
- Secret canaries across logs, events, exceptions, and rendered responses.
- Proof that subprocess, Git, Codex, brokerage, real network, and raw-artifact
  boundaries are never invoked.
- Pause/resume revision, duplicate, race, audit-event, and manager-gate tests.

## Full-suite verification

Run the complete safe suite only after all focused tests pass:

```text
TESTING=1 UNIT_TESTING=1 .venv/bin/python -m pytest -q
```

The session safety banner must report paper defaults and live brokerage calls
blocked. No real Telegram call or token may be used during any test.

## Known risks

- Telegram identity relies on account possession; it is not sufficient for
  destructive approvals.
- Telegram provides at-least-once delivery behavior, so duplicate suppression
  relies on OPS-014 delivery identities and receipts.
- Long polling requires a durable single-consumer lease to avoid competing
  adapters.
- A network outage can grow the outbox; bounded attempts, dead letters, and
  retention visibility are required.
- `/report` can leak sensitive material if it bypasses the query projection;
  raw report forwarding is prohibited.
- Existing trading Telegram notifications are unrelated and must not share
  lifecycle, messages, or tokens implicitly.
