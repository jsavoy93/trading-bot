# OPS-016 — Add audited engineering approval actions

## Objective

Add a narrowly enumerated, durable approval-request and decision protocol for
the deterministic engineering manager after the notification and read-only
dashboard layers have been proven. Human approval must bind to one exact task,
branch, action, and evidence digest; it must never become arbitrary remote
command execution.

## Priority

P2 — initially BLOCKED pending threat-model and action-policy approval.

## Owner

trading-manager

## Exact acceptance criteria

1. Approval requests are created only by deterministic manager states, identify
   one exact task, branch, workflow state, evidence digest, and enumerated
   action, expire finitely, and contain a one-time unpredictable nonce.
2. Only the allowlisted Josh Telegram identity can approve or reject; every
   request and decision is durably audited, idempotent, bounded, and linked to
   OPS-014 event causation/correlation IDs.
3. Approval never executes arbitrary commands. The deterministic manager may
   consume a decision only at an explicit matching gate after revalidating task,
   branch, workflow state, evidence digest, freshness, repository safety, and
   single-use status.
4. Initial permitted actions are an explicit minimal enum approved by Josh,
   such as resuming one blocked engineering workflow or authorizing creation of
   one review PR. Merge, push to `main`, deployment, live trading, secret or
   configuration changes, destructive operations, and TUI control remain
   unrepresentable and prohibited.
5. Telegram and dashboard read the same request/decision projection. The
   dashboard remains read-only; it gains no approval endpoint in this item.
6. Ambiguous, expired, replayed, mismatched, concurrent, malformed, stale, or
   already-consumed decisions fail closed, do not advance workflow state, and
   emit bounded audited results.
7. Approval messages contain a bounded human summary, but the decision binds to
   exact persisted evidence rather than mutable message text.
8. Approval storage is transactionally consistent with its corresponding
   event/outbox records and supports deterministic restart recovery.
9. Tests use fake identities, clocks, nonces, managers, Telegram transport, and
   stores; they invoke no real Telegram, GitHub, Git, Codex, brokerage, shell,
   network, merge, push, or deployment action.
10. Focused approval/security/manager tests pass, followed by the complete safe
    suite with live brokerage blocked.

## Security constraints

- Two-step request/confirm or request/reject flow with short expiry, one-time
  nonce, exact evidence digest, and compare-and-set consumption.
- Default deny; exact Josh chat/sender/private-chat identity required.
- No free-text action names, arguments, shell fragments, branch names, paths, or
  URLs are accepted as executable input.
- Hardcoded action enum; forbidden actions cannot be serialized into an
  approval request.
- Revalidate repository clean state and workflow identity at consumption time.
- Store no Telegram token, environment, prompt, stdout/stderr, credentials, or
  unbounded report/diff content.
- Never merge, push `main`, deploy, enable live trading, modify secrets/config,
  delete files, signal processes, or control the Codex TUI.
- Every denial and consumption result is bounded, immutable, and auditable.

## Focused tests

- Exact identity, nonce, expiry, evidence digest, task, branch, state, and action
  validation matrices.
- Replay, double decision, conflicting decision, concurrent consumer, lease,
  crash, and restart recovery tests.
- Workflow/evidence/branch changed between request and decision.
- Missing, stale, blocked, malformed, unknown, and already-consumed requests.
- Authorized approval, authorized rejection, and every unauthorized chat/sender
  combination.
- Property/table tests proving merge, push-main, deployment, live trade, secret
  change, arbitrary command, file deletion, process signal, and TUI control
  cannot be represented.
- Secret, injection, oversized input/output, and mutable-message-text tests.
- Fake-boundary tests proving no real Telegram, GitHub, Git, Codex, brokerage,
  subprocess, or network operation occurs.

## Known risks

- Compromise of Josh's Telegram account becomes a control-channel risk even
  with allowlisting; destructive actions remain excluded.
- Human-readable message content can become stale; the digest-bound persisted
  evidence is authoritative.
- Races between approval and workflow advancement require transactional
  compare-and-set semantics.
- Nonce generation and storage introduce replay and predictability risks.
- Adding actions later can silently broaden authority; every new enum member
  requires a separate reviewed backlog change and threat analysis.
- “Create PR” still changes external state and must revalidate branch/evidence
  immediately before execution.
